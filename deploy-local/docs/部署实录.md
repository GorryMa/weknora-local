# 部署实录：从零到可用，以及 7 个坑的根因分析

记录一次完整的 Windows 11 + Docker Desktop + Ollama 本地部署过程。所有结论均来自日志与实测，
而非猜测。遇到问题时按图索骥比重读官方文档更快。

**环境**：Windows 11 家庭版、WSL2、Docker Desktop 4.99、Ollama 0.40、16 GB 内存、C 盘剩余 20 GB / D 盘 200 GB SSD。

---

## 坑 1：`wsl --update` 假死

**现象**：窗口停在 4.3%，显示「60 秒后超时」。等 16 分钟无变化。

**诊断**：直接采样进程 IO，而不是靠感觉判断。

```powershell
$p = Get-Process wsl
$r1 = $p.ReadTransferCount
Start-Sleep 12
$p.Refresh()
"12 秒读取增量: {0:N1} MB" -f (($p.ReadTransferCount - $r1)/1MB)
```

结果：**增量 0 字节，CPU 时间停在 3.4 秒**。不是慢，是假死。

**根因**：`wsl --update` 从 `github.com` 下载，而当时该域名完全不可达（`curl` 返回 HTTP 000，
15 秒超时）。注意 `api.github.com` 和 CDN 是通的 —— 这说明是**特定域名被阻断**，不是整体断网。

**解法**：绕开被阻断的域名。

```powershell
wsl --update --web-download      # 先用官方备用通道
```

不行则手动装：

```bash
# 通过 API 拿到真实下载地址，再用加速镜像
curl -L -o wsl.msi "https://gh-proxy.com/https://github.com/microsoft/WSL/releases/download/3.0.5/wsl.3.0.5.0.x64.msi"
msiexec /i wsl.msi
```

**经验**：判断「卡住」不要靠等待，用进程 IO / CPU 增量做客观判断。镜像加速测速实测
`gh-proxy.com` 最快（18 MB/s），`ghproxy.net` 仅 158 KB/s。

## 坑 2：镜像全部 `not found`

**现象**：`docker compose pull` 报 `wechatopenai/weknora-app:0.9.0 not found`。

**排查**：直接查 Registry API 确认标签是否存在。

```bash
TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:wechatopenai/weknora-app:pull" | python -c "import json,sys;print(json.load(sys.stdin)['token'])")
curl -s -H "Authorization: Bearer $TOKEN" "https://registry-1.docker.io/v2/wechatopenai/weknora-app/tags/list"
```

**根因**：标签是 `v0.9.0`，带 `v` 前缀。`.env.example` 的注释里写了，但很容易漏看：

> 填写目标 release 的 git tag（如 `v0.7.0`，**注意 v 前缀**）

**连带风险**：镜像不存在时 compose 会认为「需要本地构建」，转去执行 `docker compose build`。
那是一条要处理 Go 模块代理、npm 源的编译链路，半小时起步且极易失败。**看到 not found 先查版本号。**

## 坑 3：文档解析出来没有一个字

**现象**：上传一份扫描件 PDF，状态显示「已解析」，但提问答不出任何内容。

**排查**：直接查数据库，不看界面。

```bash
docker exec WeKnora-postgres psql -U postgres -d WeKnora \
  -c "select chunk_index, length(content), left(replace(content,E'\n',' | '),150) from chunks order by chunk_index;"
```

结果：整个文档只有 **1 个片段、181 字节**，内容全是：

```
![document_page_1.jpg](resource://...)
![document_page_2.jpg](resource://...)
```

**根因**：这份 PDF 是图片型（扫描件）。WeKnora 默认把图片当作资源记录，不做 OCR，
`chunk_images` 表 0 行，向量库里自然没有文字。

**解法**：开多模态，让视觉模型做 OCR。配置存在 `knowledge_bases.vlm_config`：

```bash
docker exec WeKnora-postgres psql -U postgres -d WeKnora \
  -c "select vlm_config from knowledge_bases;"
```

关键发现：WeKnora 的代码里有一条规则 —— **`type=KnowledgeQA` 且 `supports_vision=true` 的模型，
可以直接出现在 VLLM 视觉模型下拉框里**。所以不必装本地视觉模型，云端的多模态模型就能用。

## 坑 4：界面「重新解析」无效

**现象**：开了多模态、点了重新解析，结果和第一次**一模一样**（还是 1 个片段）。

**排查**：对比 docreader 的返回。

```
第一次: content_len=166, images=3
第二次: content_len=166, images=3     ← 完全相同
```

**根因**：文档的 `metadata.process_overrides` 里存着创建时的参数快照，其中
`pdf_force_scanned: "true"`、`enable_multimodel: false`。界面按钮调用接口时不带配置，
所以永远走这份坏快照。

**解法**：显式传参覆盖。

```bash
curl -X POST "http://localhost:8080/api/v1/knowledge/$DOC_ID/reparse" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"process_config":{"enable_multimodel":true,"vlm_config":{"enabled":true,"model_id":"<id>","model_name":"deepseek-flash"}}}'
```

响应里 `process_overrides.enable_multimodel` 变成 `true` 才算生效。

结果：片段数 1 → **14**，文字量 181 字节 → **4175 字**，成功提取出「学校名称 专业 学历」
「时间区间」等结构化信息（此处不列举具体内容）。

## 坑 5：一次提问等 5 分钟（本方案最隐蔽的问题）

**现象**：问答要等 299 秒才出结果。日志拆解：

| 阶段 | 耗时 |
|---|---|
| 问题理解 | 2.3 s |
| **检索知识库** | **295.4 s** |
| 重排 / 合并 / 过滤 | 12 ms |
| 模型生成答案 | 2.0 s |

其中 `Embedding vector retrieval took: 4m54.67s` —— 生成一个查询向量花了近 5 分钟。

**逐步排除**：

1. 宿主机直连 Ollama embed → 3 秒（首次含加载），模型已常驻 → 排除网络
2. 容器内连测 3 次 → 78 / 82 / 126 ms → 排除容器转发
3. 检查磁盘类型 → SSD → 排除磁盘
4. 查 `ollama ps` → **只剩 `qwen3-4b`，`bge-m3` 不见了**
5. 查 `system_settings` / `knowledge_bases` → 摘要模型绑的是本地 `qwen3-4b`（3.89 GB）

**根因**：可用内存只剩 2.4 GB，装不下两个模型（3.89 + 1.24 GB）。Ollama 保留先加载的
对话模型，把向量模型卸载。每次检索都要从磁盘重新加载 → 80 ms 变 300 秒。**模型越大，
换出越频繁，越慢** —— 这解释了为什么「换了个更大的模型反而更卡」。

**修复**：

```bash
# 1) 摘要/辅助任务改走远程模型，不占本地内存
docker exec WeKnora-postgres psql -U postgres -d WeKnora \
  -c "update knowledge_bases set summary_model_id='<远程模型 id>' where id='<kb id>';"

# 2) 停掉空转的后台任务（重启容器最直接）
docker compose restart app

# 3) 强制卸载本地模型
curl -X POST http://127.0.0.1:11434/api/generate -d '{"model":"qwen3-4b:latest","keep_alive":0}'
```

修复后 embedding 稳定 **87 ms**。

**结论（可直接照抄的经验）**：16 GB 内存的机器，**本地只跑向量模型，对话与摘要全部走云端**。
两个本地模型同时常驻必然互相驱逐，症状是「莫名其妙卡几分钟」，且日志里看不出明显错误。

## 坑 6：文档卡在 `finalizing`

**现象**：`parse_status` 长期停在 `finalizing`。

**根因**：坑 5 的连带结果 —— 收尾阶段要调用向量模型建索引，而模型被卸载，任务一直重试。

**处置**：中断后台任务（`docker compose restart app`）后确认数据完整性，再修正状态：

```bash
# 先确认文字和向量都在
docker exec WeKnora-postgres psql -U postgres -d WeKnora \
  -c "select (select count(*) from chunks) chunks, (select count(*) from embeddings) vecs;"

# 数据完整则直接改状态
docker exec WeKnora-postgres psql -U postgres -d WeKnora \
  -c "update knowledges set parse_status='completed', summary_status='completed', processed_at=now() where id='<id>';"
```

这是「数据已好、状态没更新」的场景，改状态是安全的。若 chunks 为空，则应重新解析而非改状态。

## 坑 7：备份文件里的明文密钥

`models` 表的 `parameters` 字段以**明文**存储云端 API Key：

```json
{"api_key": "sk-****************", "base_url": "https://api.example.com/v1", ...}
```

**根因**：`.env` 里的 `SYSTEM_AES_KEY` 为空。这个变量是数据库中敏感字段的加密主密钥，
留空时不做落盘加密，于是 API Key 直接以明文存进 PostgreSQL。

**解法**：部署前显式生成（32 字节，一次性，之后不可更换 —— 换了旧密文就解不开）：

```bash
openssl rand -hex 16      # 输出 32 个 ASCII 字符，填入 .env
```

`deploy-local/setup.sh` 已自动生成该值，无需手动处理。

**注意**：
- 若密钥**从空改为有值**，此前写入的明文字段不会自动加密，需在界面上重新保存一次模型
- 若密钥**已有值再更换**，所有已加密字段将无法解密（界面显示为空），只能重填

`pg_dump` 会原样导出这些内容。因此：

- 备份文件**不能**进 Git、不能放公开网盘
- 共享 `.env` 或数据库快照前，先清空该字段
- 若曾泄露，立即到服务商控制台轮换密钥

## 验收清单

部署完成后逐项确认：

- [ ] `docker compose ps` 五个服务均 `Up`，`postgres` 为 `healthy`
- [ ] `curl http://localhost:8080/health` 返回 200
- [ ] 页面可注册登录，账号为管理员
- [ ] 模型管理里有 1 个 `KnowledgeQA` + 1 个 `Embedding`，且为默认模型
- [ ] `docker exec WeKnora-app wget -qO- http://host.docker.internal:11434/api/tags` 能列出模型
- [ ] 上传 PDF 后 `chunks` 表片段数 > 1 且包含真实文字
- [ ] 提问响应时间 < 15 秒（超过说明存在模型争抢，回看坑 5）
- [ ] `bash deploy-local/backup.sh` 能产出 tar.gz
